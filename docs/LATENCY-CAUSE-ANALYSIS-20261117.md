# 速度未達の原因調査

2026年11月17日。対象コードc39c1bf（製品コードはf27e704）。**製品コード・設定・既存の評価台帳を変更せず、追加のモデルAPI生成0回で調査しました。**

## 結論

現行の外部APIを「構造化JSONの全文受信・検証まで同期で待つ」処理に、設計の次質問2.5秒/抽出打切り3秒を割り当てています。診断10件では抽出だけで2951〜5215ms、中央値3764msでした。この時間枠との不整合が、頻繁なタイムアウトの直接原因です。

保存応答の無通信再生では、ローカルの要求組立・解析・検証はミリ秒以下が中心です。主な待ち時間はAPI往復・応答生成の区間にあると考えられます。ただし当時の通信区間を分解していないため、回線・プロバイダーの待ち行列・入力処理・生成のどれが何秒かまでは確定できません。当時のホストCPU負荷・イベントループ遅延も未記録です。

## 原因・要因の整理

通常API要求はreasoningもservice_tierも指定していません。[モデルの公式仕様](https://developers.openai.com/api/docs/models/gpt-5.6-terra)では推論量の既定値はmediumです。実際の消費は要求ごとに異なり、既定短文で0だった観測を、通常の全相談へ一般化はできません。設定を明示して比較する余地はありますが、noneでも3秒未達だったため、これだけで解決するとは言えません。

キャッシュは[一致するprefixと再利用可能な境界が必要](https://developers.openai.com/api/docs/guides/prompt-caching)です。最新入力の後に固定データを置く現在の配置は再利用を難しくする可能性があります。cached_tokens=0という結果だけから、キャッシュ改善で短縮できる秒数は推定しません。

## ローカル処理の切り分け

保存済みの修正版10応答を、現在のコードへメモリー上のResponseとして返し、各2回ウォームアップ後に20回ずつ実行しました。生成・入力計数・D1・ブラウザは呼んでいません。製品コードを変えていないため、今回の確認はこの再生・保存計測と再現用スクリプトの実行で、既存136件の製品テストは再実行していません。評価用journalのatomic write/renameは同じファイルシステムで別に20回計測しました。

cloneの時間は抽出全体に含まれ、足し合わせません。これは現在のWSL/Nodeによるwarm再生であり、当時のAPI時間から直接差し引ける内訳でも、本番cold性能でもありません。それでも、修正したローカル検証だけが秒単位の増加を生んだという説明は、この再生結果では支持されません。

DB記録も打切り範囲に含まれることは、即時のモックAPI応答＋利用量保存50ms待ちに対し、抽出期限20msを与える再現でMODEL_TIMEOUTになることを確認しました。実際のD1が50msだったという測定ではありません。

## 断定してはいけない説明

- **「品質修正で出力が長くなったので遅くなった」**：同じE01は出力268→259トークンと減っている一方、2592→4026msへ増加しています。E09も398→392トークンで3317→5215msです。修正後は入力が約170トークン増えましたが、実行時刻も異なり、入力増加と環境変動を分離していません。
- **「ローカルの判定・Queue・OCRが遅い」**：実モデルの診断時間はextractOnceまでで、次質問・業務判定・メール生成は計測終了後です。Queue・OCR・ブラウザもこの時間には入っていません。
- **「自動リトライで何度もAPIを呼んだ」**：1相談1生成で、自動再生成はありません。入力計数は生成前に行い、計測時間の外です。
- **「max_output_tokens=2048なので2048トークンを生成した」**：実出力は174〜401トークン。2048は上限です。
- **「ストリーミングにすれば全文確認も3秒になる」**：初回出力の観測や待機表示には使えますが、全文の引用・条件検証が終わる時間の短縮は別に確かめる必要があります。

## 次に進める順序

1. **区間計測を入れる。** 要求開始、ヘッダー、最初の出力、全文受信、検証、利用量保存、案件保存、画面操作可能までを分け、リクエストIDと一緒に残す。API応答待ちの中で何が遅いかを先に切り分ける。
2. **安全性を維持して入出力を短くする。** 対象に不要な属性辞書、サーバーで導ける重複値、繰返しキー等を見直す。引用・単位・訂正・品目の検証は省かない。静的情報と動的情報を分け、キャッシュの実ヒットも測る。
3. **同条件で比較する。** モデル・推論量・service tier・入力・出力契約を明示し、同じ相談でTTFT/全文完了/品質を比較する。通常設定と診断設定の差を残さない。3秒期限を延ばして速くなった扱いにはしない。
4. それでも時間枠に入らない場合に、受付と抽出完了を分ける方式を設計判断として検討する。今回は実装・設定を変更していない。

この順序は[公式の遅延計測・最適化方針](https://developers.openai.com/api/docs/guides/latency-optimization)とも整合します。追加生成が必要な比較は、既存の予算台帳を引き継いだ別の実行として扱います。
