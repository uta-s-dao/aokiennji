# UTA-10：受付通知・送信履歴・再試行

問い合わせ・見積依頼を保存するトランザクションで、社内向けの通知待ちイベントも作成する。通知イベントの作成に失敗した場合は受付全体がロールバックし、受付成功とは返さない。メール送信は受付のトランザクション外で行い、Resendの障害によって保存済みの受付を失わない。

正式見積の発行はDB内の状態変更であり、顧客へのメール送信ではない。初期範囲の顧客宛メールは担当者が手動で送付する。

## 設定

初期値はメール無効。次をサーバーの秘密設定へ登録し、許可された検証先で確認してから有効化する。既存の会社メールやDNSを無断で変更しない。

| 変数                       | 用途                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `EMAIL_DELIVERY_MODE`      | `live` の場合だけ実送信。未設定・`disabled` ではDBに保留                                               |
| `RESEND_API_KEY`           | 送信と送信元ドメイン取得が可能なサーバー専用APIキー。送信権限だけのキーではドメイン取得ができない      |
| `RESEND_DOMAIN_ID`         | Resendで登録した送信元ドメインのUUID                                                                   |
| `RESEND_FROM`              | 表示名を含めない送信元メールアドレス                                                                   |
| `INQUIRY_NOTIFICATION_TO`  | 明示的に指定した担当者の通知先1件。受付フォームに入力された顧客アドレスは使用しない                    |
| `APP_ORIGIN`               | HTTPSの管理画面オリジン。ローカル検証のみlocalhost/127.0.0.1のHTTP可。パス・認証情報・クエリを含めない |
| `RESEND_WEBHOOK_SECRET`    | Webhook署名鍵。APIキーとは別の秘密値                                                                   |
| `NOTIFICATION_CRON_SECRET` | 起動API専用のランダムな32文字以上の秘密値                                                              |

`npm run db:migrate` で `202610210002_notifications.sql` を適用する。本番マイグレーションには既存手順の本番適用承認が必要。ブラウザー用ロールから通知テーブルを直接読む権限はない。

通知送信時にResendのドメイン取得APIを呼び、ID・送信元アドレスのドメイン一致・`verified`・送信機能有効を確認する。未検証・取得失敗時は送信せず、管理画面へ直近の確認結果を表示する。管理画面にAPIキーやWebhook署名鍵は返さない。

送信本文は受付種別・受付番号・ログイン必須の管理画面リンクのみ。氏名、連絡先、相談本文、顧客用の見積トークン、会話の社内メモは含めない。

## 起動とWebhook

- `POST /api/notifications/deliver`：`Authorization: Bearer <NOTIFICATION_CRON_SECRET>` が必須。URLに秘密を埋め込まない。GETは提供しない。
- `GET/POST /api/admin/notifications`：管理セッション必須。変更は同一オリジン・頻度制限付き。
- 管理画面 `/admin?tab=notifications`：「通知待ちを送信」で1回分を実行、「再試行」で未送信通知を再予約して1回分を実行する。各実行は最大3件。ほかの通知待ちが先に処理される場合がある。
- `POST /api/notifications/webhook`：Resendからの到達通知。Svixの署名・時刻検証を未加工の本文に対して行い、検証成功後にJSONを解析する。256KiBまで。検証失敗は400、署名鍵未設定は503。

ResendのWebhookには `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.complained`, `email.failed`, `email.suppressed` を登録する。他イベントは無視する。DB処理が失敗した場合は5xxを返し、Resend側の再配信対象にする。イベントIDで重複を排除し、API応答より先に届いたWebhookも後からメールIDに結びつける。保存するのはイベントID・メールID・種別・日時で、Webhook原文の個人情報は保存しない。

定期起動の実配備は **UTA-11**。ここでは起動経路のみ実装し、定期送信が稼働したとは扱わない。利用枠の通知はUTA-9の `/api/billing/notifications` で別管理する。

## 再試行・重複防止

DBの受付ID別一意制約と、永続化した通知IDから作るResendの冪等キーを併用する。行ロック・期限付きリース・更新時のリース照合で並行ワーカーを制御する。送信中にプロセスが停止しても2分後に同じキーで再試行できる。

送信元・宛先・本文は初回試行時に固定し、JSONB保存後もフィールド順を固定して同じリクエスト本文を送る。途中で送信元・宛先の設定が変わった通知は「要確認」に止める。再試行で新しい通知IDや冪等キーへ自動的に変更しない。

通信切断・429・5xxなど結果不明の失敗には、1分から最大1時間の指数バックオフを使う。送信結果不明は配信されていない証拠ではない。認証・入力等の確定的な拒否、12回の試行上限、初回試行から23時間経過のいずれかで「要確認」に止める。Resendの保持期間24時間を超えて自動再送しない。未試行の通知は受付から何日経っていても初回送信できる。

「要確認」「処理中」「送信受付済み」は管理画面から再送できない。要確認になった場合は次の手順で対応する。

1. 受付ID・通知ID・ResendのメールIDと履歴を照合し、担当者が受付内容を確認する。
2. 結果不明の場合はまずResend側の履歴・到達通知を確認する。通知行を削除したり、初回試行日時をリセットして再送しない。
3. 通知の再送が必要なら、受信有無と宛先・原因を確定した上で別途操作を設計する。今回の画面は曖昧な通知を強制再送する機能を提供しない。受付対応と顧客宛の手動連絡は継続できる。

## 状態の読み方

管理画面は最新100通知と、その最大12回ずつの試行履歴を表示する。`送信受付済み` はResend APIの受付成功。`到達確認` はメールサーバーが受理した状態であり、人が閲覧した証拠ではない。後着の `sent` や到達遅延で到達済みを戻さず、不達・苦情等の問題状態を優先する。

## 実接続の残条件

環境台帳ではResend接続が保留中で、会社の送信元ドメインと通知先は未指定。会社確認事項は既存のQ009（通知先・担当）、Q014（送信元・DNS）、Q018（障害対応）に集約済み。この実装は会社確認済みの運用条件や有料契約を意味しない。

実際の受信先の到達確認、本番Webhook登録・署名鍵設定、本番マイグレーション、公開Workerでの動作確認は未実施。本番接続後、指定先での受信確認とResendの到達イベントを照合して初めてUTA-10の実到達条件を完了とする。

公式仕様：[冪等キーの24時間保持](https://resend.com/docs/dashboard/emails/idempotency-keys)、[Webhook署名検証](https://resend.com/docs/webhooks/verify-webhooks-requests)、[送信元ドメイン取得](https://resend.com/docs/api-reference/domains/get-domain)、[メール送信](https://resend.com/docs/api-reference/emails/send-email)。導入済みSvix 2では `verify` は署名検証のみ行うため、成功後に本文をJSON解析する。
