# 新しい取扱可否確認システムの合格条件

設計版1.1。ここに記載する試験は、これから作るアプリの受入条件であり、実施済みの試験結果ではない。設計資料自体の検証結果はVALIDATION.mdに分ける。

## 1. 判定の考え方

顧客の目的は「少ない手間で、当社で対応できるかを知り、必要ならメールへ進むこと」。返答が生成された、表示が完了した、単体テストが通っただけでは合格にしない。

各ケースで、入力、使用したルール・資料の版、画面、公開API、保存された現在値、調査呼出し記録を照合する。既知の期待文をそのまま返すモックだけで、実モデル・実資料の合格を代用しない。

重大な誤肯定、根拠のない対応外、条件混入、機密漏洩、勝手なメール送信は受入試験内で0件を必須とする。これは将来の誤りが0件という保証ではない。

## 3. 実モデル・実資料・実UIの検証

単体試験後、修正用に使っていない新しい相談で少なくとも次の5経路を通す。

1. メーカー・型番が明確で、追加質問なしに判定する。
2. 名前不明の交換部品を用途と写真から調査へ進める。
3. 図面付き製作相談で、寸法訂正を途中に入れる。
4. 二つの部品を同じ案件で扱い、数量と条件が混ざらない。
5. 未登録分野・資料不足・API失敗からメール文作成まで進める。

上記の経路に、依頼範囲・支給/調達方式の変更、図面の差し替え、部品別の塗装/配送条件、分野内でも個別条件は確認待ちとなるケースを含める。REVIEW-20261116.mdのメール由来例は既知の設計・回帰資料であり、独立未知評価の20相談とは分ける。

各経路に表現違いを含め、合計20相談を初期の独立評価セットとする。固定コード・固定知識版で実施する。質問作成者へ期待文言や修正内容を渡さず、評価結果は正誤・負担・速度を別記する。別エージェントを起動することは必須ではなく、人による評価でもよい。

顧客役は、説明せずに操作できるか、同じことを聞かれないか、結果から次の行動が分かるかを確認する。会社担当者は、結論が社内の実判断と一致するか、メールで再度聞く必要がある情報が適切にまとまっているかを確認する。

実在資料の確認権限がない場合、デモで機能合格まで進められるが、事業上の実用合格と分ける。

## 4. 計測

| 指標 | 定義 |
| --- | --- |
| 次質問までの時間 | 送信/選択から次質問の入力が可能になるまで。ネットワークと描画を含む |
| 調査時間 | 調査受付から結果表示まで。queue待ちを含む |
| 取扱可否到達時間 | 初回入力から結論表示まで。顧客の入力時間を含む値と除いた値を両方記録 |
| 質問数 | 最初の自由入力の後に表示した質問数。確認・言い換えの再質問も数える |
| 離脱 | 聞き取り開始案件のうち結果にもメール導線にも到達していない割合。観測期間を併記 |
| 判定精度 | 会社の正解ラベルと照合。誤肯定・誤否定・不要な確認待ちを分ける |
| 自動判定率 | 完了案件中のcan_handle/out_of_scopeの比率。正解率と同時に見る |
| 分野の確認率 | 有効な根拠でscopeAssessmentを確定できた比率。個別依頼の自動判定率へ合算しない |
| 問い直し | 回答済み・unknown・skippedを再質問した回数 |
| 費用 | 観測できたモデル/検索等の利用量と実課金。返らない利用量は不明と記す |

選択系100操作、自由文30入力、調査20案件を初期の速度測定標本とする。cold/warm、端末、回線、リージョン、モデル、失敗率、標本数を併記する。標本が少ないp95を将来性能の保証にしない。

現行との比較は同じ相談集合・資料条件・測定方法で行う。旧本番へ無断の大量送信をしない。比較不能なら新方式単独の測定結果として報告する。

## 5. 公開の判定

- 必須機能ケースを満たし、重大な誤判定・混入・漏洩がない。
- 実モデル評価を行い、実用目的の達成を確認する。モック結果だけでは不可。
- 対象となる主要相談で、会社承認済みの実資料と判断の一致を確認する。
- 単に全案件をneeds_reviewへ送る実装は合格としない。supported/excludedの実根拠があるケースを正しく判定する。
- 速度の目標を満たすか、未達箇所と実測値を示して公開可否を判断する。未達を無言で合格に変えない。
- 本番の宛先・利用枠・資料利用範囲・保管方針・管理者認証を設定済み。
- 新URL、実結果、残る制約、入口の戻し方が確認可能。

実装完了、デモ合格、制限付き実用評価合格、本番切替完了を別の状態として報告する。
