# 別モデル向け実装指示

設計版1.1。アプリ本体は未実装。この文書は、ユーザーが設計を採用して実装を依頼する際の手順と開始指示である。設計の見直しへの了承だけを、アプリ実装・公開・メール送信・既存システム変更の承認と解釈しない。

## 1. 最初に守る境界

- 新しい空のリポジトリへ実装する。推奨 `/home/uta/aoki-availability-v2`。
- この設計フォルダを新リポジトリの `docs/design/` にコピーする。原本は保持する。
- 旧 `/home/uta/aoki-product-discovery-20261026` は変更しない。旧コードを読むことも実装の前提にしない。
- 旧chat/consultation/inquiryのコード・プロンプト・補正ルール・テスト期待文言を移植しない。
- ユーザーの目的は「少ない質問で取扱可否を早く知り、メール相談へつなぐこと」。自由会話機能を追加しない。
- 価格・注文・仕入先への実照会・メール自動送信を実装しない。
- 実サービスの契約・課金上限・本番入口を勝手に変更しない。ローカル試作と検証は独立して進める。

## 2. 設計資料の使い方

DESIGN.md、contracts.schema.json、ACCEPTANCE.mdの順で読む。examples.jsonは架空データであり営業情報にしない。

REVIEW-20261116.mdで実メール由来の判断範囲も確認する。契約IDは2、ResearchBrief.schemaVersionも2。版1.0の例と混用しない。scopeAssessment、assessmentScopeは必須であり、単なる日本語表示の変更ではない。

スキーマは主要な通信・データ形状の契約。SQLスキーマ、内部のEvidence、認証情報、モデルprovider用JSON Schemaまで完成しているという意味ではない。追加の内部型は定義してよいが、公開契約や判定の意味を黙って変えない。

スキーマだけでは表せない次の検査をコード化する。

- 品目ID・フィールドキーの一意性と参照先の存在。
- 根拠引用が対応する顧客入力にあり、値と属性の意味が一致すること。
- 型番、寸法種別、単位、必須条件、取り消した値の扱い。
- ルールの承認・有効期限・原資料の利用許可・coveredFields・競合。
- business_scopeとrequestのルールの区別、分野対象と個別依頼の結論の整合。
- 依頼範囲・材料手配・製作除外・図面改訂・部品別条件。過去の一時辞退や買い手としての行動を取扱ルールへ一般化しないこと。
- 各品目の結論と案件全体の結論の整合。
- inputRevision、knowledgeRevision、job期限とleaseの整合。
- 公開URL・根拠の公開範囲・顧客ごとの所有権。

## 4. 実装の順序

### 段階1 契約と判定の核

新プロジェクトを用意し、互換性を確認した依存をlockする。contracts.schema.jsonからランタイム検証・型を作り、許可された属性辞書と単位辞書を定義する。まず以下を純粋関数として作る。

- `applyInput`：変更案を検証して現在値とイベントを作る。
- `chooseNextQuestion`：質問設定と不足項目から一問または調査を選ぶ。
- `makeResearchBrief`：現行条件を凍結する。
- `decideAvailability`：分野と個別依頼を別々に検証し、依頼範囲・支給/調達方式・必須条件からscopeAssessmentとverdictを作る。
- `toPublicResult`：公開allowlist DTOを作る。
- `makeMailDraft`：現在の顧客向け情報から件名・全文・mailtoを作る。

この段階でI01〜I09、I13〜I15、S01〜S06、S09〜S10、R01〜R21のロジックを架空データで確認する。request_scopeとmaterial_supplyの値は属性辞書で検証する。LLM接続より先に、根拠のない肯定・否定が出ない核を成立させる。

### 段階2 聞き取りから結果までの画面

一問画面、写真・図面アップロードの表示、部品別の入力修正、調査中、分野と個別条件を分けた結果、メール作成・コピーを作る。結果の不足項目から対象の修正欄へ移れるようにする。先に偽の調査adapterで一連の流れを動かす。

PCとスマートフォンでI10〜I12、M01〜M05、U01〜U02を確認する。メールの宛先は明示デモ値か未設定。試験時に実メールソフトや外部送信を起動せず、リンク内容を検査する。

### 段階3 独立保存とジョブ

新D1/R2/Queueのローカルbindingを使い、案件所有権、revision、冪等性、outbox、lease、期限を実装する。ブラウザの接続に調査の寿命を依存させない。

J01〜J09、P01、P04〜P05を失敗注入で確認する。更新0行が成功扱いになるCASの穴、queue重複、遅い旧結果の上書きを先に塞ぐ。各機能のHTTP正常系だけで終えない。

### 段階4 実モデルによる自由文抽出

現時点で利用できるモデルの公式仕様を確認し、抽出専用adapterを作る。モデル名は設定で変更可能。成功時は一回で型を返し、失敗時の追加生成ループを作らない。

モデルに質問順、取扱可否、同意、送信を決めさせない。選択式入力ではモデル0回を計測する。F01〜F02と、表現違いを含むS01〜S06を実モデルで確認する。キーや予算が未提供ならローカルの他段階を進め、実モデル試験は未実施として残す。

### 段階5 承認資料と一括調査

資料登録・ルールのCSV/JSON取込、検証プレビュー、承認・撤回、期限、公開説明を実装する。承認時に分野/個別依頼と対象の方式・範囲を確認できるようにする。過去メールの依頼・確認中・一時辞退を自動で現在の取扱ルールにしない。未承認原本を公開APIへ直接返さない。

登録資料検索、必要時の外部検索、本文抽出、写真/PDF解析をadapterとして接続する。本文取得とモデル呼出しの上限はDESIGN.mdの共通予算を守る。取得結果は対象・属性・根拠箇所を保持する。

新規外部APIや有料サービスを勝手に契約しない。外部検索の接続が不足している場合は明示し、登録資料だけのルートと失敗表示を先に完成させる。

R01〜R21、F03〜F04、P02〜P03、P06を確認する。資料が足りないこととコードが壊れていることを分けて報告する。

### 段階6 独立評価と制限付きプレビューの準備

ACCEPTANCE.mdの実モデル・実資料・実UIの検証を実施し、計測結果を残す。使い慣れていない人の操作と会社担当者の正誤判断を含める。未知の質問を出す評価者へ過去の期待文言を渡さない。

合格後、デプロイ設定・必要な環境変数一覧・リソース一覧・公開範囲・戻し方を用意する。ユーザーの実行指示がある場合だけ制限付きプレビューを配信する。アカウント確認と費用・権限が必要な未設定があれば、具体的な作成対象を示す。

一般公開や旧入口切替は、プレビューの評価と会社設定がそろった後の別判断とする。

## 5. 検証コマンドの契約

実装時に次のnpm scriptsを用意し、何を検証するかREADMEへ記載する。ここに書かれたコマンドが現時点で存在・実行済みという意味ではない。

| コマンド | 対象 |
| --- | --- |
| npm run typecheck | 型整合 |
| npm run lint | 実装規約・明らかな問題 |
| npm run test:domain | 質問、更新、判定、メール、公開DTO |
| npm run test:integration | ローカルDB・queue・競合・所有権・API |
| npm run test:e2e | PC/モバイルの一連操作 |
| npm run test:contracts | スキーマ・妥当例・不正例 |
| npm run test:isolation | 旧コード・API・DB・Cookieへの依存検出 |
| npm run build | 固定依存でのビルド |
| npm run eval:live | 明示指定の評価環境で実モデル評価。費用上限必須 |

本番への試験送信は既定で無効。外部サービス未設定の試験を成功に置き換えない。該当の未実施項目を結果に残す。検証中にコードを変えたら影響する検証だけやり直し、合格版を特定する。

## 6. 完了報告に必要なもの

- 新リポジトリと起動方法。変更は新システムだけであること。
- 4プロフィールの画面と、メール文まで進む実演。
- テスト結果と実モデル評価結果の区別。
- 実測の質問数・待ち時間・誤判定・未判定理由。
- 実資料で判断できる範囲と、会社確認待ちの範囲。
- 分野だけ確認できた案件と、今回の個別依頼まで判定できた案件の区別。部品別条件と依頼方式がメール文にも維持されること。
- 残る未設定、公開可否、入口切替を実施したか。

「全テスト成功なので実用完成」「架空ルールで動いたので当社の商品を判定できる」「メールボタンを押せたので送信済み」と報告しない。
