# 取扱可否を短時間で確認する新システムの設計

作成日：2026年11月15日。更新日：2026年11月16日。設計版：1.1。

お客様が短い質問に答えた後、まとめて調査し、アオキエンジで対応できるかを確認する独立アプリを作る。見積・注文は扱わず、必要な内容をメール相談へ引き継ぐ。既存チャットへの追加改修はしない。

ユーザーの「おすすめで」に基づき、次の設計判断を採用した。この資料の作成は完了しているが、アプリの実装・本番公開・既存入口の切替はまだ行っていない。

| 項目 | 採用する設計 |
| --- | --- |
| お客様の体験 | 短い聞き取り → 一括調査・結果表示、の2段階 |
| 質問 | 一度に一つ。回答済みを飛ばす。「分からない」「この内容で調べる」を用意 |
| 依頼範囲 | 商品購入、加工、製作を区別。必要時だけ客先支給・自社調達を確認 |
| 調査への移行 | 最低限の識別情報がそろい、判断を変える重要な未回答項目がなくなった時。質問上限でも進む |
| 速度 | 選択式はAIを呼ばない。自由文も原則1回の抽出だけ。外部調査は第2段階に限定 |
| 結論 | 取扱分野の確認と、今回の仕様・依頼範囲・納期での結論を分ける。調査障害は別表示 |
| 対応分野 | すべての取扱分野の相談を受け付ける。自動で肯定・否定するのは承認済みの判断資料がある範囲 |
| 分離 | 新リポジトリ、新Worker、新DB、新保存領域、新セッション。旧チャットのコード・状態・設定・APIは流用しない |
| 試用 | 別URLの制限付きプレビュー。実データと実利用で合格した後、入口の切替を別途判断 |
| メール相談 | 入力済み内容を含むメール作成＋全文コピー。メールはお客様が送信する。添付は自動送付しない |
| 今回の成果物 | 設計書、契約スキーマ、例、受入条件、別モデルへの実装指示 |

## 読む順序

1. [DESIGN.md](DESIGN.md)：目的、画面、質問・判定ロジック、独立構成、API、データ運用。
2. [contracts.schema.json](contracts.schema.json)：主要データと公開レスポンスの機械可読な契約。
3. [examples.json](examples.json)：架空データによる入力・結果例。営業情報として使わない。
4. [ACCEPTANCE.md](ACCEPTANCE.md)：合格条件と検証シナリオ。
5. [IMPLEMENTATION.md](IMPLEMENTATION.md)：実装順序、完了条件、別モデルへの開始指示。
6. [VALIDATION.md](VALIDATION.md)：設計資料に対して実施した検証と、実装後に残る検証。
7. [REVIEW-20261116.md](REVIEW-20261116.md)：実メールに基づく見直し根拠と代表相談の流れ。

仕様の意味はDESIGN.md、フィールド名・型・列挙値はcontracts.schema.json、合否はACCEPTANCE.mdを基準とする。矛盾があれば実装担当は黙って独自解釈せず、仕様差分として記録し、この3点を整合させる。

版1.1では `ItemResult.scopeAssessment` と `CapabilityRule.assessmentScope` を追加し、契約IDとResearchBriefのschemaVersionを2へ更新した。版1.0の契約・例とは互換でない。アプリ本体と実データは未実装のため、今回データ移行は発生していない。配布用最新版は `availability-v2-design-20261116-v1.1.zip`。旧 `availability-v2-design-20261115.zip` は版1.0として保持する。

## 重要な判断

「Webで商品を見つけた」「仕入先一覧に載っている」だけでは、当社の取扱対応可能としない。会社が承認した取扱範囲と、お客様の必須条件が合うことを根拠にする。在庫確保、正式な納期、見積金額はこのシステムの回答対象に含めない。納入日等が必須条件として提示された場合は、その条件が未確認のまま全体を対応可能にしない。

毎回「担当者にお問い合わせください」に戻るだけでは目的未達。公開前に、会社承認済みの実資料を使って、実際に自動判定できる相談と確認へ回す相談の範囲を検証する。

## 実装の渡し方

このフォルダ全体を新しい実装チャットへ渡し、IMPLEMENTATION.md末尾の開始指示を使う。既存実装を貼り付けたり、この評価用フォルダにアプリ本体を作ったりしない。新しい実装先の推奨は `/home/uta/aoki-availability-v2`。同名の作業があれば上書きせず、別の空ディレクトリを選ぶ。

実装モデルは自由に選べる。担当を増やすことは前提にしない。初めは一つのモデルで、段階ごとの合格条件を確認しながら実装する。
