# 設計資料の検証記録

2026年11月16日。対象は設計版1.1の資料一式。アプリ本体は作成していない。

## 今回実施した確認

| 確認 | 結果 |
| --- | --- |
| JSON Schema Draft 2020-12としての定義検査 | 成功。契約IDは2、ResearchBrief.schemaVersionは2 |
| examples.jsonの正常例 | 14例すべて、対応する契約に適合 |
| examples.jsonの不正例 | 10例すべて、対応する契約で拒否 |
| 受入ケースのID | 73件、重複なし。今回10件追加 |
| Markdown内の相対ファイルリンク | 参照先が存在 |
| コードブロックの開始・終了 | 対応確認 |
| テキストの文字化け検査 | 置換文字なし |

JSON検証にはPythonのjsonschema Draft202012ValidatorとFormatCheckerを使用した。正常例には、依頼範囲と当社調達の入力、分野承認ルール、方式を限定する対応外ルール、分野内でも個別依頼は確認待ち、分野内でも今回の方式は対応外、過去の照会だけでは分野も未確認となる例を含む。すべて架空データである。

不正例には、根拠なしの分野肯定、分野対象外・未確認なのに個別依頼を肯定する組合せ、判定対象assessmentScopeのないルール、旧版の調査入力の無変換混用を追加した。

request_scopeやmaterial_supplyは一般のField型で表現するため、キーごとの許可値、根拠引用との意味の一致、支給品と材料全体の違いはスキーマだけで検査できない。実装時のランタイム検証とI14〜I15、S09〜S10等で確認する。今回それらのアプリ試験を実行したわけではない。

## 実装後に確認すること

- 目標レスポンス時間、実モデルの日本語抽出精度、実UIの操作性。
- 会社の承認済み実資料による取扱分野と今回の個別条件の判断の正しさ。
- 依頼方式変更、部品別条件、図面改訂、明示訂正、メール文の整合。
- 所有権、公開範囲、DB競合、queue重複、期限切れ、訂正後の旧結果排除。
- 実端末のmailto互換性と全文コピー、管理者認証、運用設定。
- 現行方式に対する時間・質問数・離脱・判定品質の比較。

73件は定義した受入ケース数であり、実装試験が73件合格したという意味ではない。JSON Schemaの適合も意味の正しさや会社の取扱承認を保証しない。今回読んだメール由来の例は既知の資料で、未知の独立評価の合格には数えない。
