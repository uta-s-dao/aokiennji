# 登録情報・37参照サイトを優先する商品調査と、回答ごとの出典記録

登録済みの情報を先に使い、確認できなかった場合だけ外部Webへ広げるよう変更した。実際に従業員が発注先の確認に使っている参照サイトを優先する。ただし、登録先であることから在庫・発注条件まで承認済みとは判断しない。

## 検索する順序

1. 「情報源・取込」の有効な登録商品・取込資料を型番で照合する。一致した資料は取得元・原文抜粋・登録日時を保存する。販売価格を仕入価格へ転用しない。
2. 承認済み仕入先一覧の参照サイトと、有効なWeb情報源・参照ドメインを優先検索する。現在の一覧は、重複を除く39URLのうち巡回保留の2件を除いた37ドメイン。今後追加された有効な情報源も対象になる。
3. 登録参照先で型番が一致した商品は、通販ボタンがなくても担当者が照会できる候補に残す。在庫表示なしは未確認を維持する。欠品・販売終了や型番不一致、取得失敗などで候補を確認できなかった場合は次へ進む。
4. 同じ型番の調達実績があれば、そのURLを再取得して確認する。過去の数量・在庫・承認を現在の条件にコピーしない。
5. 外部Webを検索し、型番・末尾仕様・購入窓口を検査する。拡張した理由も記録する。

37サイトを検索対象として全件指定する。検索エンジンが返す候補ページを照合する方式で、37サイトの全商品を毎回巡回する処理ではない。従来の20ドメインでの打ち切りをなくし、100件を超える登録ドメインは分割して扱う。HTTPの参照先も扱い、外部アクセスのIP・リダイレクト検査を適用する。

管理者向け補助調査も登録先を先に調べ、必要な項目が未確認の場合に外部検索へ進む。お客様向けの在庫・発送日の確約や、仕入先への注文送信はこの検索から行わない。

## 社員が会話の根拠を確認する場所

管理画面の「相談・引継ぎ」から会話を開き、各回答の **「この回答の情報源・検索経路」** を展開する。「AI利用記録」から回答を選んで会話詳細を開く場合も同じ記録を確認できる。

- 回答当時の優先参照先と、保留した参照先。
- 登録情報・優先参照先・過去の調達先・外部Webを調べた順序、検索語、開始・完了日時、取得候補URL、失敗・拡張の理由。
- 検索APIが返した検索語と参照URL、優先対象外として除外したURL。APIが返す参照URLと、アプリが本文を取得して照合したURLを分ける。
- ページごとの採用・型番不一致・取得失敗、原文抜粋、HTMLハッシュ、掲載在庫・数量。
- OpenAIへ渡した回答用の根拠、サーバーの確定案内、採用した段落と根拠ID。
- 同じ商品の直前の調査を再利用した場合は、その調査IDと元の取得日時。

情報源や資料が更新・無効化されたら、以前の検索判断をそのまま再利用しない。保存済みの記録は当時のスナップショットとして維持する。記録開始前の会話の出典は復元しない。

出典記録は社内向けの保存メッセージと調査メモに保存する。公開チャットの応答・履歴には含めず、認証済みの会話詳細APIで取得する。APIキーは記録しない。

今回の実API10問も **管理画面「相談・引継ぎ」の「チャットの履歴」 `/admin?tab=conversations`** に追加した。既存の相談12件、型番中心の検証10件、顧客会話検証10件の計32件を同じ一覧に表示する。検証の行には「実API検証」または「顧客会話検証（5往復）」と表示する。各行を開くと、実際の質問・回答・出典・検索経路・APIの失敗理由を共通の会話詳細で確認でき、検証記録のJSONも保存できる。専用の検証セクション・メニューは廃止した。`conversation` パラメーター付きURLで会話を直接開け、従来の検証URLも同じ履歴へ移動する。

管理者認証済みの `/api/admin/conversations` と会話詳細APIで、通常の相談と保存済み検証記録をまとめて返す。アーカイブの原本は変更せず、顧客データベースへの重複登録もしない。検証の調査メモは閲覧専用とし、架空の取込資料や試験条件から実発注・見積を作成する操作は表示しない。公開チャットから検証記録は取得できない。

統合後はPC・スマートフォンのE2E計8件が成功。履歴一覧から検証10件すべてを開き、通常の相談の保持、実回答・出典の照合、解析失敗の理由、JSON保存、会話URLと再読み込み、未認証の401、公開チャットへの非表示、画面幅を確認した。関連ユニットテスト3ファイル10件と型チェックも成功。実際の3000番環境でもPC・スマートフォンから22件の一覧と会話詳細・参照元URLを確認し、結果とスクリーンショットを `.data/verification/source-priority-2026-10-18/unified-admin/` に保存した。

OpenAIの検索では、APIの[参照URLを返す機能](https://developers.openai.com/api/docs/guides/tools-web-search)を使用する。ドメインフィルターを利用できるモデルには指定し、それ以外でも検索先を指示したうえで、アプリ側で対象外のURLを除外する。モデルの出力だけで出典URLを採用しない。

## 相談窓口の表現と見積までの流れの改善（2026-10-18）

「担当者にご相談ください」という返信を、当社の窓口として「当社で確認します」「お見積りを承ります」と答える方針に変更した。AIであることは偽らない。返信の後ろに毎回追加していた「現時点では必要数量分の在庫・発送日は未確定です」は廃止し、取得できた掲載情報と次の操作を案内する。

OpenAIの検索では在庫・数量・出荷・納期も検索語に含める。最新の在庫を明示的に調べる依頼では、登録資料や調達候補の発見だけで検索を終えず、必要に応じて一般のWebへ広げる。取得ページの型番と在庫・配送表示はJevで照合する。公開するのは掲載上の状態・数量・調達先出荷の目安で、仕入先名・URL・仕入価格・原文は調査メモに保持する。複数社の在庫を加算せず、一つの掲載元の情報を一組として示す。一般の配送案内と別商品の情報は個別商品の納期に転用しない。

質問は一つずつにし、選定チェックリスト全体の説明をやめた。条件がそろえば見積依頼フォームへ案内する。同じ調査結果の再掲を減らし、入数と小分け販売、調達先出荷と顧客への到着の違いには短く直接答える。途中の品番訂正、メーカー変更なしという短い返事、製作相談でも数量と配送先を保持し、フォームへ渡す。全周長不明の平ベルトについては、設備の停止と全周の測定を案内し、コンベヤの端間距離やプーリーの円周と混同する回答を修正した。
