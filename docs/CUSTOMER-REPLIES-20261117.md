# お客様向けの返答と保存・判定・メールの接続改善

2026年11月17日。作業基点378e8ce、未コミットの変更。検証したsrc全体のdigestとPC/モバイルの実表示・保存値・メールは[JSON記録](CUSTOMER-REPLIES-20261117.json)、短い読み物は[トーク記録](CUSTOMER-TALK-20261117.md)にあります。

## 変更した動作

- 保存前後の現在値から、品目名・保存した値・訂正内容を短く返します。APIはDBへのcommit成功後に通知を返し、画面はその通知を表示します。入力不足、保留、読み取り失敗を保存成功の文章にしません。
- 質問に品目名を付け、一問ずつ聞きます。不明・スキップと最大6問の扱いは維持します。
- 結果には、今回の指定数量・温度・希望日など、資料で確認できなかった具体条件を示します。分野判定と個別依頼の結論を分け、次の行動を画面とメールに同じ文言で示します。
- missingFieldsは顧客が未入力または競合している属性に限定しました。入力済みでも会社側の根拠が足りない値は、この欄へ戻さず結果理由で説明します。資料で対応できることを確認できない限り、needs_reviewを維持します。
- 指定済みの配送先など、必須扱いではない情報も結果の条件一覧で確認できます。必須かどうかの判定は変更せず、長い表示値には省略を明示し、メールには全文を保持します。
- 方式限定の対応外では承認済みの公開説明を使います。調査失敗、期限切れ、矛盾、未確定入力を別の理由で説明します。
- デモ用抽出器で句点の後に別部品が続く入力を分け、部品別の塗装・配送先を保持するようにしました。保存済みLuna応答6件の回帰に加え、同じ複数品目の入力を実画面でも確認します。
- デモ用抽出器で、用途への質問中に温度を訂正すると、その訂正文を用途欄にも保存する経路を実UIの画像で発見しました。他の属性を解釈した発言を、未回答の質問への回答へ流用しないよう修正し、用途を実際に答えたときだけ保存することを確認しました。
- 調査failedで品目can_handleのまま理由コードだけRESEARCH_INCOMPLETEへ変わり、公開契約違反となる経路も修正しました。失敗時は業務上の肯定を返しません。

返答は保存状態・理由コード・承認済み公開説明から決定的に組み立てます。返答文のための追加モデル呼出しはありません。公開契約版2とDBスキーマは維持しました。160文字の保存通知、120文字の質問、300文字の結果理由の上限も検証します。

## 検証の限界

今回はローカルの架空データと保存済み応答による機能検証です。新しい実モデル出力の品質・速度、会社実資料による判断一致、独立未知相談、本番運用は未評価です。以前の実API6回や40/40の台帳、通常プレビューの使用済み3回枠を変更していません。外部検索と添付内容解析等の未接続機能も、接続済みとはしていません。

本番公開・モデル採用切替・外部リソース作成・課金設定変更・メール送信・既存チャットの変更は行っていません。ローカルの返答と既存機能の接続改善が今回の完了範囲です。
