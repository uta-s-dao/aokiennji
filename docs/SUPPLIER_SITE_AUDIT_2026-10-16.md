## 現在のJevとWeb取得の役割

- Jevは、相談の分類、取得した商品ページと型番の一致、調査結果の判定を担当する。Jev自体に39サイトを自動巡回して発注する機能を委ねてはいない。
- 検索はOpenAI／Exa／Tavily、ページ取得はアプリの `safeFetch` とHTML解析が担当する。
- 仕入先一覧の社名・取扱分野・URLは、取扱分野の判断や調査先候補に使う情報。登録されたことは、商品の在庫・取引条件の確認や発注の承認を意味しない。
- 未登録型番は登録先ドメインに限定せず検索する。発見した商品は調達候補であり、自動で確定在庫や販売納期にしない。検索からの実発注処理はない。

## 実験の方法と限界

通常DB `.data/aokienji.sqlite` の `supplier_knowledge` を読み取り専用で開いた。全41件にURLがあり、アルセラ／アルメディオ、エムコマース／MCCトレーディングがそれぞれ同じURLだった。取引先の統合・URLの差し替えは実施していない。

公開ページだけをGETで確認した。最初の巡回は1URLあたり登録ページと製品リンク最大3ページ、HTTP取得は現在の商品調査と同じ5秒・2MB・リダイレクト3回まで。robots.txtを先に読み、取得条件が確認できない2URLは本文の自動巡回を止めた。robots.txtの取得成功や未設置は、継続利用の許諾があるという判定ではない。

最初の巡回では本文取得116回（同じページへの転送を含む）が成功した。さらにアルメディオ、イーデンキ、マグテック、タキゲンを各最大4ページ追加確認し、通販ページ・製品詳細・断熱材の導線も点検した。下表のページ数は2巡回で実際にHTTP 200を取得した最終URLの重複を除いた数。MCCトレーディングと不二鉱材はWeb閲覧ツールでは公式サイト本文を確認できたが、アプリの巡回成功には数えない。

これは全参照URLの点検と製品ページの標本調査であり、全商品のクロールではない。ログイン後の在庫・発注API、画像・PDFだけの情報、JavaScriptで後から表示する値、各社との自動取得契約は未確認。サイト全体に在庫情報がないと断定する試験でもない。

## 誤案内につながる具体例

1. **標準品の印と箱の入数**：[アジア技研のスタッド一覧](https://www.asiagiken.co.jp/products/product01.html)には、○は標準対応を示すもので在庫保証ではなく、在庫の問い合わせが必要と明記されている。小箱1000個などの入数も、在庫1000個という意味ではない。
2. **材料在庫と完成品在庫**：[並田機工のアンカーメタル](https://namitakiko.co.jp/product/anchor)には材料在庫、受注生産、一部サイズの即納対応が併記されている。「豊富な在庫」という会社紹介から全仕様の完成品が即納可能と判断できない。
3. **仕入先の標準出荷と当社発送**：[イーデンキ](https://www.edenki.co.jp/)の一般案内は標準出荷が注文後約1～10営業日。特定商品の必要数量がその期間で揃うという回答でも、アオキエンジから1週間以内に発送できるという回答でもない。
4. **本文が取得できても値が揃わない**：イーデンキの商品詳細2ページには静的HTMLに在庫状況の見出しがあるが、必要数量を保証できる値を取得できなかった。タキゲンのA-452詳細も静的取得では在庫・納期の値がなく、ブラウザーの追加確認は20秒でタイムアウトした。取得成功を在庫確認へ昇格させない。
5. **参照先そのものの照合**：[石松測器の登録先](https://www.shigotomarugoto.info/JobOffers/view-c?company_id=IIS068002)は求人・企業紹介、九州黄銅は商工会議所の企業紹介。安達屋金物の登録URLは現在「利作カンパニー」の紹介を表示する。紹介文の取得と正式発注先の特定を分ける。

マグテックの `/shop` は追加のブラウザー確認でHTTP 200だったが、今回の表示から必要数量の在庫・発送日を確認していない。イーデンキの商品詳細もブラウザーで開き、一般出荷案内までを確認した。これらの追加閲覧で購入・問い合わせは行っていない。

## Jevの実APIによる補助実験

取得済み37サイトから各1ページを選び、公開本文の先頭最大6000文字をJev `jev-latest` へ渡した。質問は「特定商品の完成品在庫数量が明記されているか」「10個全数の当社向け引当と、当社から顧客への発送期限の両方が明記されているか」の2つ。robots未確認の2サイトはスキップした。8リクエストすべてHTTP 200。

今回の標本では37ページすべて、両質問で採用しきい値0.8に達しなかった。在庫数量のスコアは0.02～0.30、当社発送確認は0.01。この数値はモデルの判定値であり、在庫の実在確率・納期の保証率ではない。商品ごとの在庫・納期をJevだけで承認する仕組みにはしていない。

併せて次の架空6ケースを同じAPIへ渡し、すべて想定どおりに判定された。この架空データを販売条件・実在の仕入先回答として保存していない。

| 架空ケース | 数量の記載あり | 全10個の引当と当社発送確認あり |

| 商品掲載のみ・在庫表示なし | いいえ | いいえ |
| 在庫あり・最短当日出荷、数量不明 | いいえ | いいえ |
| 在庫2個・必要10個、残り納期不明 | はい | いいえ |
| 標準品○・小箱入数1000、在庫保証なし | いいえ | いいえ |

## 在庫表示がない場合・少量在庫の場合の処理

| 取得した情報 | 内部での扱い | お客様への案内 |
| --- | --- | --- |
| 在庫記載なし・JavaScript未取得・通信失敗 | 在庫未確認。0個へ置き換えない | 希望数量を受け付け、在庫と発送予定を確認する |
| 在庫あり、数量不明 | 掲載上の在庫あり。必要数の可否は未確認 | 発送日を確約せず、必要数と条件を照会する |
| 少量在庫、必要数を下回る | 数量不足。残りの調達・加工・分納条件を確認 | 全数揃う時期の確認前に一律の日数を出さない |
| 欠品の明示 | 掲載上の欠品。更新日時を残す | 次回入荷日や代替先を確認する。一定日数で埋めない |
| 取り寄せ・受注生産 | 必要数の生産／手配日数を確認 | 個別の見積・納期確認へ引き継ぐ |
| 数量十分、当社向けの引当なし | 他注文で減る可能性がある参考在庫 | 正式見積・注文前に再確認する |
| 必要数の確保・経路・発送条件を担当者確認済み | 有効期限内の確認情報として利用 | 会社の承認済みルールに従って概算・正式見積を案内する |

未確認時の案内例：

> お取り寄せ・お見積りのご相談を承ります。現時点では必要数量分の在庫・発送日は未確定です。ご希望数量の在庫と発送予定日は確認後にご案内します。

確認に何時間かかるかも、会社未回答のため約束しない。余裕日数を一律で追加しても、そもそも必要数が確保できない状況は解消しない。

## 納期遅延を避けるために確認する順序

1. 型番・仕様・数量・入数・配送先を特定する。
2. 仕入先に、必要数量の調達可否、引当／確保の有無、仕入先の出荷予定を確認する。在庫照会APIや契約CSVがあればWeb表示より優先する。ただし照会と引当は別。
3. 当社経由なら、仕入先出荷→当社入荷→検品・加工・梱包→当社発送→顧客到着を分ける。直送なら直送先と輸送条件を確認する。
4. 会社が決めた営業日・休業日・締切・追加日数・確認有効期限で概算する。仕入先の出荷日を当社発送日や顧客到着日へ流用しない。
5. 正式見積・注文時に数量と出荷条件を再確認し、変更時は以前の概算を失効させる。遅延の判明時には担当者が顧客へ連絡する。

引当の証跡、仕入先回答番号、具体的な当社発送日の専用入力・変更検知・自動遅延通知までは、現状のシステムにない。現在は担当者の確認チェックと調達可能数量・配送営業日数・確認日時で管理している。仕入先APIとの連携、問い合わせ担当、確約してよい根拠、遅延連絡手順はQ006・Q007・Q009の会社回答後に具体化する。今回の変更だけで納期遅延が起きなくなるとは扱わない。
