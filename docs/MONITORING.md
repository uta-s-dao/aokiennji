# UTA-12：運用画面と外部監視

## 実装範囲と配置状態

`/admin?tab=monitoring` に利用枠・使用／予約額、AI・調査の有効状態、提供元の最後の接続確認、メール・ジョブ・バックアップの判定、外部監視の最終受信・反映版・通知状態・障害／復旧履歴を集約する。上限変更・停止／再開、接続試験、受付通知の再試行、同期・バックアップ履歴、監査へ同じ管理画面から進める。

2026-10-21、ユーザーの残作業実施指示により、変更前の暗号化バックアップ取得後に004を本番へ適用し、PR #21の実装を既存Workers URLへ配置した。配置版は `3ff6a971-8475-4a21-b905-63f8222c7b8d`、URLは https://aoki-enji.official-b.workers.dev/admin?tab=monitoring 。監視用秘密を登録し、本番API・設定保存・認可・監査・セッション失効・PC／スマートフォン表示を確認済み。

現在のWSL作業端末に、作業ツリーとは別の永続配置とユーザーsystemd timerを用意し、約1分間隔の暫定監視を稼働させた。独立プロセスからの監視と本番への結果記録を連続3回確認したが、この端末を停止すると監視も止まる。常時稼働先の確定と監視ホスト自体の監督は未完了。実通知の受信先・使用を許可された認証済み送信元も未確定で、メールは無効のまま。正式ドメインとDNS・Resendドメイン認証は後日対応。未接続・送信無効・監視対象外を正常稼働や到達確認と扱わない。

## 設定と認証

外部監視の通知先、障害・復旧の連続回数、ジョブ遅延、バックアップ遅延はPostgresへ保存する。更新版で競合を拒否し、設定と操作者の監査を同一トランザクションで保存する。管理APIはサーバー側の管理セッション必須。変更にはOrigin確認・入力上限・頻度制限を付ける。同期などの手動ジョブは実行前に操作者と要求内容を監査し、実行結果はジョブ履歴で確認する。一般設定の保存と監査も同一トランザクションにし、API接続試験は開始と結果を監査する。

既存認証は8時間のDBセッション、HttpOnly・SameSite=Lax・本番Secure cookie。ログアウト、DB側失効、期限、パスワード／署名秘密の変更で失効する。個人別の権限・MFAは未実装であり、共通資格情報を持つ全員が同じ管理権限を持つ。利用人数と方式の確定はQ018。担当者・代行者は会社判断まで確定しない。

機械監視専用の32文字以上のランダムな `MONITOR_SECRET` を独立ホストとWorkerの秘密管理へ入れる。ジョブ秘密や管理者cookieを転用しない。`GET /api/monitor/health` と `POST /api/monitor/report` はBearerヘッダーを定時間比較で検証し、クエリの秘密は受け付けない。応答はno-store。未認証時はDBへ接続せず401。ヘルスはDBを読むだけで、有料API・メール・同期を起動しない。DB読取りに失敗すると詳細を含まない503を返す。履歴取込は固定形式・容量制限・一意IDを使い、内容のすり替え・状態の巻戻しを拒否する。

## 独立ホスト

`npm run monitor` を、サイトと本番DBが止まっても動く**別の管理されたNode 24ホスト**から起動する。ブラウザーを開いておく必要はない。監視ホストは本番DB接続・管理者パスワード・顧客情報を持たない。専用SQLiteには設定キャッシュ、連続観測回数、障害番号、最小限の通知履歴・送信先を保存する。Web DBのSQLite代替ではない。保存領域と秘密ファイルは所有者限定で保護し、保持期間未合意のため自動削除しない。

独立ホストにリポジトリと依存を用意し、`.env.example` の `MONITOR_*` だけを専用の `/etc/aoki/monitor.env` に設定する。CLIはサイトの `.env.local` を自動読込しない。

- `MONITOR_ORIGIN`：監視対象のHTTPS originだけ。ユーザー情報・パス・クエリ・フラグメントは拒否。リダイレクト先へ秘密を転送しない。既存Workers URLでの受入も可能。
- `MONITOR_SECRET`：Workerと同じ秘密。変更時は両側を更新して認証成功を確認する。
- `MONITOR_STATE_PATH`：絶対パス。例 `/var/lib/aoki-monitor/state.sqlite`。状態を失うと障害の重複抑制も失うため、再配備で初期化しない。別originに同じ状態を再利用しない。
- `MONITOR_EMAIL_MODE=live`、`MONITOR_RESEND_API_KEY`、`MONITOR_RESEND_DOMAIN_ID`、`MONITOR_FROM`：監視ホスト専用の送信設定。各送信前にResendのドメインID・名前・verified・sendingを照合する。無効時は履歴を保持し、送信しない。
- `MONITOR_BOOTSTRAP_TO`：初回接続前からサイト停止中の場合に限る初期宛先。正常なヘルスを一度受信した後は保存済み設定を使用する。保存済み宛先が空なら初期宛先へ勝手に戻さない。
- `MONITOR_ALLOW_LOOPBACK=true`：明示した合成試験のループバックHTTP用。本番はfalse。

登録前に一度手動実行し、管理画面の最終受信・送信設定・設定版を確認する。`infra/operations/monitor.service.example` と `.timer.example` は未登録のテンプレート。ユーザー／絶対Nodeパス／配置場所を実行先に合わせ、会社確認後に `/etc/systemd/system/aoki-monitor.service`／`.timer` へ設置する。`systemctl daemon-reload` と `systemctl enable --now aoki-monitor.timer` の後、`systemctl list-timers aoki-monitor.timer`、`systemctl status aoki-monitor.service`、`journalctl -u aoki-monitor.service` で起動を確認する。

監視ホスト自体の停止・ディスク枯渇・タイマー停止は、そのホストだけでは通知できない。別サービスのmissed-run／ホスト監視を設定してから本番受入とする。Resend全体が停止した場合の連絡経路もQ018で確定する。未登録のOnFailureサービスを通知済みの根拠にしない。費用が発生するホスト・監視サービスの契約はQ015の予算確認後。

## 判定と通知

各回に `/`、`/admin` のHTTP成功・HTML種別と、認証付きヘルスを確認する。HTTP正常は画面の全操作の成功保証ではない。サイト／管理画面停止と、DB読取失敗、受付・利用枠メールの再試行／要確認、API枠到達、定期処理失敗／遅延、バックアップ失敗／遅延を区別する。ヘルスの認証・形式エラーは「外部監視の接続」として扱う。DB停止中は他のDB依存項目を未確認とし、復旧したと推測しない。

APIの管理者停止・メール無効・バックアップ監視無効は対象外表示。メール設定だけ存在し、ドメインの接続確認がない場合は未確認。ジョブは直近の実行結果とscheduled履歴の両方を使い、手動実行でCron停止を隠さない。期限切れ整理の1日周期を考慮する。バックアップは0時間で対象外、正の値を設定後は記録なしも要対応にする。成功記録だけで別保管先や復元可能性を保証しない。

初期案は3回連続失敗で障害、2回連続正常で復旧。同じ障害は1回にまとめ、正常／不明／無効は連続失敗を中断する。不明／無効から復旧通知は出さない。復旧後の再障害には新しい番号を作る。timer案は起動完了から60秒後に次の起動を行うため、検知時間は応答・タイマー・閾値に依存する。3分以内などの保証はしない。

外部キューはサイト停止中にも送信し、復旧後に未取込履歴を最大100件ずつ再送する。同期できなくても外部送信は止めない。同時起動は別のSQLiteロックDBが排他し、プロセス終了時にOSが解放する。業務状態DBは別なので、送信前の固定宛先・送信元識別子・最初の試行時刻・通知IDがクラッシュ後も残る。

Resendには同じ通知IDと固定本文を冪等キー付きで再送する。1回の起動で送信試行は最大5件。指数バックオフ、最大12回、最初の試行から23時間の安全期限を用いる。送信結果不明時に宛先や送信元を変えたものは自動送信を止めて要確認にする。未試行の通知は設定待ちとして保持する。障害通知が未処理の間は同じ障害の復旧通知を先に送らず、障害通知が要確認なら復旧通知も要確認とする。APIの送信受付を実メール到達・閲覧と混同しない。

## サイト停止中の手順

1. 外部メールの障害番号・対象と、独立ホストの最終起動／ローカル状態を照合する。管理画面を開くことを復旧の前提にしない。
2. サイト停止ならCloudflare DashboardのWorkers & Pagesで対象Worker `aoki-enji` の配備・エラー・アカウント状態を確認する。Hyperdrive接続・同時接続数も確認する。戻す場合は既知の配備版とDB互換性を確認してから行う。
3. DB障害ならSupabaseの対象プロジェクト `aoki_enji` の稼働／休止・接続数・障害状況を確認する。公開や支払い状態を勝手に変更しない。復元が必要なら `docs/OPERATIONS.md` の手順を使い、別環境へ復元・照合してから切替判断する。
4. 通知障害ならResendのドメイン認証、送信履歴、受信拒否と提供元状態を確認する。独立監視の状態DBで `events` の通知ID・試行時刻・statusを読み、Resendの `aoki-monitor-<通知ID>` と照合する。秘密・受信先・メール本文を公開ログへ貼らない。要確認の行を削除／pendingへ戻して再送しない。結果を確定し、担当者が別の一回限りの連絡を行って記録する。
5. API上限なら管理画面復旧後に使用／予約・未精算を照合し、提供元の利用／請求画面も確認する。上限変更や有料契約は会社権限者が決める。予約を削除して上限を回避しない。
6. ジョブ／バックアップならタイマー・Cron・実行履歴・別保管先・鍵・ディスク状態を確認する。DNS・契約・支払い・APIキー変更は各サービスで権限者が実施する。正式ドメインの作業は再開指示後。
7. 原因解消後、外部で連続正常と復旧通知を確認する。履歴の取り込み、通知元の送信受付と受信先での到達を別々に確認し、対応担当者が受入結果を残す。

## 残る受入条件

Q014／Q015／Q018に基づく、使用を許可された送信元・受信先、常時稼働する独立実行先・費用・主担当と代行者・判定条件・監視自体の監督・別連絡経路、共通管理者方式の適否。指定先への障害／復旧の実メール到達、常時稼働先での定期実行と停止／復旧の受入、正式URLへの切替後の再確認が残る。004の本番適用・Worker配備・専用秘密・現WSL端末での暫定timer稼働は確認済みで、これらを未実施の作業として繰り返さない。実到達と常時稼働の受入を省略してUTA-12全体を完了にしない。

参考：[Resendの冪等キー](https://resend.com/docs/dashboard/emails/idempotency-keys)、[systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)。
