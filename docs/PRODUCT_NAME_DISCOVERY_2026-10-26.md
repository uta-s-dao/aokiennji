# 商品名から仕入先掲載を照合する修正

## 確認した原因

本番DBにはキューセキの仕入先URLと「パッキン等」が登録されていたが、該当商品の登録・商品ページ本文はなかった。該当会話では商品名を認識した後に登録商品の照合だけで終了し、検索段階の記録は空だった。

元の作業フォルダーには多数の既存変更と旧版があるため、最新の公開版相当コミット `329d6aa01697e4d218cb54284248260e33100919` を基に `/home/uta/aoki-product-discovery-20261026`、ブランチ `fix/product-name-discovery` で実装した。元フォルダーのコードは置き換えていない。

## 動作

- 承認済み登録商品で特定できない商品名・シリーズ名・材質名を、仕入先の掲載索引に照合する。商標記号・空白・英字大小・全角半角の差を吸収する。
- 商品名と型番は同じ表の行、または同じ構造化Productレコードから取得する。ページ内の近くの数字を型番として推測しない。
- 商品ページの取込結果は既存documentsテーブルの専用索引として保持する。自社の承認済みproductsへ自動登録しない。通常の資料検索や型番検索からは分離し、鮮度と利用権限の確認を迂回させない。
- 外部検索が有効なら登録仕入先を優先して検索し、関連サイト最大2件を巡回する。外部検索プロバイダーの失敗時も、取扱分野に合う登録先の巡回は継続する。
- 巡回は同一登録ドメイン、商品リンク、深さ2、通常8ページ、1サイト20秒まで。手動取込は最大20ページまで指定できる。robots.txt、既存の安全なHTTP取得、取込停止先の指定を適用する。外部カタログへのリンクを無条件で巡回しない。
- 未検索・取得失敗・確認範囲内の該当なしを区別する。仕入先の掲載だけでは当社の販売可否・現在庫・仕様適合を確定しない。仕入先名・URLは管理者向けの照合記録に保持し、顧客向け結果には商品名・掲載型番・掲載確認日だけを出す。
- 再読込時も索引の鮮度・情報源の有効状態を再確認する。回答生成AIにはこの確定済み照合結果を言い換えさせない。

## 索引の初回作成と更新

対象環境のDB接続を指定した上で、登録ドメインを明示して実行する。検索・在庫表示・販売承認の設定は変更しない。

```sh
npx tsx scripts/refresh-supplier-catalog.ts --domain kyu-seki.jp --max-pages 16
```

ローカルでは次を使用する。

```sh
node scripts/database-local.mjs npx tsx scripts/refresh-supplier-catalog.ts --domain kyu-seki.jp --max-pages 16
```

初回取込済みのサイトは、既存のsyncジョブで通常の同期対象がない回に、24時間を超えた掲載情報を1サイトずつ更新する。既存の5分ごとの定期実行を再利用するため、新しいスケジュールは不要。定期実行の稼働を前提とし、失敗は既存のジョブ履歴・障害通知に残る。7日以上更新できていない索引は照合根拠に使わない。未取込の全仕入先を自動で巡回し始めることはない。

巡回上限・サイト側の制限により全商品を収集できる保証はない。一般的な本文だけで商品と型番の対応を確定できない場合は、確認不能として扱う。

## 検証と反映状態

実サイトのトップページから限定巡回し、検証用DBに7ページ・36レコードを取り込んだ。時間制限等による未完了2件・残りページあり。目的の商品は取得でき、商品名の表記違いと9007 / 9007-LC / 9007-SCの4ケースを照合した。この検証をサイト全体の収集完了とは扱わない。

新規・関連テスト7ファイル85件が成功。型チェック、vinextビルド、git diff --checkも成功。結果ログは作業ディレクトリの `.verification/` に保存した。広めの検証に含めた既存のsourcing / preferred-sourcingテストには9件の失敗があり、変更前の同一コミットでも同じ9件が失敗することを確認した。今回の追加処理による失敗ではない。

本番へのデプロイ、本番DBへの索引初回取込は未実施。反映時は両方が必要。会社への販売条件の確認や、外部AI検索の有効化を前提にせず、取り込んだ索引で今回の商品を照合できる。
