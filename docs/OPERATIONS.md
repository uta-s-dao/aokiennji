# UTA-11：定期処理・バックアップ・復元

## 現在の状態

ドメインに依存しない実装と分離環境の検証を行う。本番マイグレーション、ジョブの実配備、実メール到達、正式URLへの接続切替は未実施。UTA-10の既存ローカル実装を必要な範囲だけ取り込み、元の作業場所は変更していない。

会社ドメイン・ResendのDNS認証・既存会社メールのDNSは後日対応。無料／有料プランの契約・変更も行わない。頻度・保存期間・復旧目標・通知先・費用は会社確認事項Q009／Q014／Q015／Q016／Q017／Q018を原簿とし、ここに書いた案を承認済みと扱わない。

## 実行する処理

| 処理 | 用意した実行頻度の案 | 1回の内容 |
| --- | --- | --- |
| 情報同期 | 5分ごとに期限を確認 | 有効なURL情報源のうち各情報源の更新間隔を過ぎた1件。最も古い試行を優先し、失敗した情報源による独占を防ぐ |
| 受付・障害通知再試行 | 5分ごと | UTA-10の永続キューから最大3件。指数バックオフ・23時間の安全期限・設定変更時停止を維持 |
| 期限切れ整理 | UTCの日付枠ごとに1回 | 有効期限切れのセッション・取込プレビュー・頻度制限だけを削除 |
| DB／Storageバックアップ | 毎日03:15 JSTの案 | 別の管理されたNode環境から実行。頻度と復旧目標は未合意 |

相談・会話・見積・監査・AI利用記録・通知履歴・冪等キー・原本・バックアップを期間未合意のまま自動削除しない。期限切れ整理は、既存の技術的な有効期限にのみ従う。同期件数が増えた場合は、処理遅延と実測負荷を見て頻度や実行先を調整する。

`/admin?tab=jobs` に最新100件の実行状態・開始／終了・件数・障害通知状態を表示する。管理者の同一オリジン操作で同期／通知再試行／期限切れ整理を1回実行できる。バックアップ／復元をWebから起動する機能は提供しない。

## 起動・認証・排他

`POST /api/jobs/run` は32文字以上の `JOB_CRON_SECRET` と `Authorization: Bearer ...`、`JOBS_ENABLED=true` の両方が必要。GETを公開せず、URLやクエリに秘密を書かない。管理APIは管理セッション必須、変更はCSRF確認・頻度制限・入力検査付き。

Cloudflare Workerにはプラットフォームの `scheduled` ハンドラーも用意する。`wrangler.jsonc` の `triggers.crons` は空のまま。実配備時にマイグレーション・秘密設定・起動認証を検証したうえで、`JOBS_ENABLED` と `*/5 * * * *` のCron Triggerを設定する。HTTP起動とscheduledの両方を登録する必要はない。CloudflareのcronはUTC。環境変数の明示設定、Workersの実行制限と実測所要時間、失敗時の再実行を公開環境で受入確認するまで「稼働済み」としない。

PostgreSQLの共通トランザクションadvisory lockにより、Web／scheduled／Nodeバックアップの同時実行を拒否する。ロック用接続と業務処理のトランザクションを分け、送信後の失敗が通知の固定済み本文や冪等キーを巻き戻さない。プロセス／接続終了でロックを解放し、次の実行が未完了記録を「中断・要確認」にする。時間だけで実行中ロックを奪うリースは使わない。通知個別のリース・フェンシングはUTA-10のまま維持する。

同じ処理・UTC時刻枠の一意制約でschedulerの再配信を重複実行しない。失敗・設定待ちの枠を即時繰り返すのではなく次の枠で再評価する。手動実行は別の実行番号を作る。処理途中の外部取得とDB接続の双方が異常になった場合は、履歴・情報源履歴・通知の試行履歴を照合する。外部APIを含む全体のexactly-onceを保証するものではない。

`npm run sync` も同じジョブ経路を使い、実行履歴を残す。CLIの1回も情報源1件が上限。

## 障害通知

失敗・中断を記録するトランザクションで、同じ通知キューに障害イベントを保存する。連続失敗は1つの障害としてまとめ、成功を挟んだ新しい失敗では新しい通知を作る。保存する通知本文は実行番号と認証必須の管理画面リンクだけ。例外全文・接続文字列・顧客本文は含めない。

送信は既存のドメイン検証・冪等キー・Webhook・再試行を使う。`EMAIL_DELIVERY_MODE=live` とUTA-10のメール設定に加え、有効な `JOB_ALERT_TO` の明示設定が必要。受付用宛先へ障害通知を自動転用しない。未指定・無効・メール無効ならキューに保留する。送信受付と到達・閲覧を混同しない。

DB／Worker／ジョブそのものの停止時は、このキューも動かない。サイト外部監視はUTA-12の対象。Node実行環境の `OnFailure=` も独立した連絡経路に接続する必要がある。`infra/operations/backup.service.example` の `aoki-backup-failure.service` は参照名だけで未実装・未登録であり、通知済みとは扱わない。主担当・代行者・連絡経路はQ018の確認後に接続する。

## バックアップの範囲

- DB：`app_private` 全体と `app_migrations`。相談・見積・設定・独自セッション・通知・ジョブ履歴・画像のBYTEAを含む。`pg_dump --format=custom` とexported snapshotで整合したスナップショットを作り、各テーブルの件数と行内容のダイジェストを記録する。
- Storage：全bucket設定と現存オブジェクトをAPIで別取得。パス・MIME・バイト数・SHA-256を暗号化したmanifestへ記録。前後の一覧を照合し、途中に変更があれば完了manifestを作らず失敗する。
- 対象外：Supabase管理スキーマ全体・Authのユーザー／設定・組織ロール／パスワード・プロジェクト設定・秘密値・DNS・削除済み／過去版オブジェクト・ローカルにしかないファイル。現在のアプリ認証は独自セッション。秘密設定と実行ロールは別途復旧する。
- 現行アプリのサイト画像はDB内のBYTEA、取込資料は抽出結果を保存する。保存していないアップロード原本をバックアップで復元することはできない。必要な原本の保管範囲と既存資料はQ017で確定する。Storageに保存された原本は全件コピー対象になる。

DBとStorageをまたぐ原子的スナップショットは提供しない。本運用では**受付・アップロード・同期・通知等の書込を停止**して取得し、前後一覧照合を補助確認に使う。Storageを同名・同内容で再作成する等の競合を一覧照合だけで完全検出できるとは扱わない。

各artifactをAES-256-GCMで暗号化し、暗号化manifestを最後に作る。保存先は新規ディレクトリのみ、権限700／ファイル600。鍵はbase64の32バイトを別の秘密管理へ置き、バックアップと同じ場所に保存しない。鍵を失うと復元できない。途中失敗のディレクトリを成功バックアップとして扱わず、ディスク使用量を別監視する。保持期間未合意のため自動削除しない。

## Node実行手順

`pg_dump`／`pg_restore`（DBと同等以上の対応版）とNode 24、プロジェクト依存を用意する。Webのruntimeロールとは別に、必要スキーマを読めるバックアップ用DB接続とStorageサーバー資格情報を秘密管理から渡す。遠隔DBはverify-full TLS必須。接続情報をコマンド引数・ログ・Gitに載せない。`BACKUP_PG_BIN` はバイナリがPATHにない場合のディレクトリ。

```sh
# 秘密設定は事前に環境へ注入する。値をここへ直接書かない。
node --import tsx scripts/operations.ts backup /separate-protected-destination/new-backup-directory
```

必要な変数は `.env.example` の `BACKUP_*`。バックアップ実行先DBには003までのマイグレーションが必要。CLIは同じ排他制御と履歴記録を使い、失敗は非ゼロ終了する。`BACKUP_RUN_SLOT` を指定すればrunner再配信も重複排除できる。

systemdのservice／timerと `backup.sh` は**未導入のテンプレート**。専用ユーザー・600の環境ファイル・別保管先・容量監視・独立したOnFailure通知を用意してから導入する。Nodeを動かす常時実行先と別保管先の契約・費用は未確定。今回それらを新規作成・有料契約していない。

## 別環境への復元

自動ツールの復元は、元とは別の空の**ループバックDBとStorageサービス**に限定する。遠隔本番へ直接復元する機能は用意しない。本番復旧は別途、対象・停止手順・バックアップ時点・秘密設定・ロール・実行先をレビューして計画する。

1. ソースと別のローカルSupabaseを起動し、DBにはアプリ／migrationスキーマを置かず、Storageも空にする。
2. 元と同じ暗号鍵を秘密管理から読み込み、`RESTORE_DATABASE_URL`／`RESTORE_STORAGE_URL`／`RESTORE_STORAGE_KEY` を渡す。
3. 全artifactを認証・SHA-256照合してから、DBを単一トランザクションで復元する。壊れたartifactはSQL実行前に拒否する。
4. DBのテーブル数・全行ダイジェストを照合し、アプリ用ロールへの権限を再設定する。Storageのbucketを作成し、原本をupsertなしで登録して再取得したバイト列をSHA-256照合する。
5. DBとStorage両方が確認できた場合だけ成功とする。復元途中にStorageエラーが出た先は「途中状態」であり、空の新しい検証先からやり直す。
6. アプリの起動・管理認証・受付・画像・原本の参照を点検する。本番を再開する前には復元されたセッションの失効、実行中ジョブの照合、通知の送信済み／結果不明とResend側履歴の突合が必要。**過去のバックアップをそのまま本番送信につなぐと重複送信の恐れがあるため、復旧時はメール・Cron・実注文を無効に保つ。**

```sh
node --import tsx scripts/operations.ts restore /separate-protected-destination/backup-directory
```

成功時に検証結果の件数を復元先のジョブ履歴へ追記する。`restore-verification.json` には検証日時と件数だけを記録する。実際の復旧時間や許容データ損失幅は、この試験だけで本番の保証値にしない。

## 分離環境の検証

`AOKI_LOCAL_DATABASE=aoki_uta11_dev` を指定すると、`scripts/database-local.mjs` はループバック接続を保ったまま専用DB名へ切り替える。元の共用ローカルDBをテストでtruncateしない。

バックアップ受入用ヘルパーは、2つの**空のStorageを持つ別ローカルSupabase**の状態ファイルを明示的に要求する。架空の問い合わせ・DB画像・非公開Storage原本を作り、暗号化・別環境復元・全テーブル内容照合・原本ハッシュ照合・同一先／非空先拒否を実行する。秘密の状態ファイルや生成キーをGitに入れない。

```sh
BACKUP_SOURCE_STATUS_FILE=/private/source-local-status.json \
BACKUP_TARGET_STATUS_FILE=/private/target-local-status.json \
node scripts/verify-operations-backup.mjs
```

検証結果は `.data/verification/uta11/restore-report.json`。生成されたDBと復元先Storageは検証専用で、削除時は同じヘルパーの生成名と記録を照合する。検証キーはローカル秘密領域、暗号化artifactはGit対象外の `.data` に置く。
