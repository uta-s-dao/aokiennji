## 回答と取込の動作

- 自社台帳と承認済み仕入先の確認情報を優先する。Web検索で商品を見つけただけでは販売可能と回答しない。
- Jev/Geminiは質問の分類・抽出に使う。販売可否、単価、在庫、金額計算、注文条件は登録情報とサーバーのルールで決める。外部APIが未設定・失敗した場合も社内検索を続ける。
- 同じ情報源・メーカー・型番の商品を更新する。異なるメーカーの同じ型番は別商品として保持する。似た型番を完全一致として扱わない。
- 取込プレビューは先頭20行を返し、確定時に全行を処理する。ファイルは10MB、表は5,000行・100列まで。
- 確認日がない情報を取り込んだ日時だけで「確認済み」にしない。URLから更新した商品は再承認が必要。取得失敗時は以前のデータを残し、失敗を履歴に記録する。
- 文書は根拠として検索する。非公開文書の本文・ファイル名は公開回答に出さない。画像だけのPDFはOCRが必要な旨を表示する。
- 専用見積リンクの発行後は金額明細を固定する。顧客が送信した価格で受注しない。顧客の注文依頼を重複送信しても注文を増やさない。

## 確認する手順

1. `npm run setup` → `npm run dev`。既に設定済みの場合、setupは既存設定を上書きしない。
2. http://localhost:3000 で「DEMO-GLASS-01を取り扱っていますか？」と相談する。
3. http://localhost:3000/admin へログインする。パスワードはローカルの `.local-admin.txt` を参照する。
4. 「情報源」でExcel/CSV用の情報源を追加し、`public/templates/` のテンプレートで取込を試す。確認日は実際に確認した日に直す。
5. 「商品」で取込結果・公開区分・承認・確認日を点検する。
6. 「設定」で必要な機能を有効にし、相談・見積発行・顧客リンク・注文承認を試す。初期状態の注文はデモ記録になる。

## 本番接続に残る作業

実装済みアプリへ会社固有の情報を接続する作業が残る。

- 実商品台帳、メーカー・仕入先、販売単価、確認周期、公開可能な項目を登録する。
- 使用するAI/検索サービスのAPIキーを設定し、実際の問い合わせ例で抽出精度・費用を評価する。選定理由は [情報取得とAIの比較](AI_AND_SOURCE_STRATEGY.md) を参照。
- 仕入先の注文API仕様に合わせてWebhookの形式・署名・重複防止を接続検証する。独自ERP/OAuthやログイン必須サイトは専用コネクターの追加が必要。
- 定期同期はcron等から `npm run sync` を実行する。管理画面で周期を登録するだけで常駐スケジューラーが起動する構成ではない。
- 画像資料の読取が必要な場合はOCRを追加する。現実装はテキスト抽出可能な資料に対応する。
- 保存先は永続ディスクを持つ単一Nodeサーバーを用意する。複数インスタンス運用にはDBとジョブ実行基盤の変更が必要。
- 公開ホスト、ドメイン、正式な個人情報取扱方針、バックアップ、運用担当を設定する。
- 実発注には `DEMO_MODE=false` と `ALLOW_LIVE_ORDERS=true` に加え、承認済み仕入先・注文・有効データ等の条件が必要。今回、実発注、メール送信、既存ドメインへの公開は行っていない。
