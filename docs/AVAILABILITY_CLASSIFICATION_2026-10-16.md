# HPの在庫・配送表示を仕分ける精度の改善

前回の2問は、在庫数量の記載と当社向け引当・当社発送の確認を診断するものだった。通常の仕入先HPには当社の引当や発送予定は載らないため、HP表示の仕分けにそのまま使うには情報が少なかった。今回は、**ページの根拠を抽出し、型番に対応する在庫・数量・配送表示を別々に判定し、正解例と比較して改善する仕組み**をアプリへ追加した。

## 今回できるようにしたこと

| 判定する対象 | 仕分け・保存する内容 |
| --- | --- |
| 掲載在庫の状態 | 在庫あり、在庫僅少、欠品、取り寄せ／入荷待ち、予約、受注生産、販売終了、表示未確認、記載の矛盾 |
| 掲載数量 | 数量と単位。入数・価格・材料の総量・別商品の数量を除外する |
| 出荷・配送の記載 | 仕入先の出荷／発送、お届けの記載、一般配送案内、未確認 |
| 判定の根拠 | ページ内の該当文・表の行・構造化データ、位置、デコード後HTMLのハッシュ |
| 判定の方法 | ルールで抽出、ルールとJevで照合、判断を保留。保留した理由も残す |

管理画面のAI調査メモに在庫の仕分けを表示し、「在庫・配送表示の仕分けと根拠を開く」で確認できる。調査メモのコピーにも根拠が含まれる。既存の保存済みメモを書き換えず、新しい商品調査から適用する。15分の再利用対象となる直前の調査は、期限が切れるまで以前の内容が使われることがある。

## 抽出と判定の流れ

1. 商品の型番が一致する構造化データ、表の行、主商品の説明から在庫・配送に関する箇所を抽出する。先頭6000文字だけで切らず、後方の表示も探す。
2. 表は列名とセルを対応させ、説明リストは「項目名：値」の区切りを保つ。関連商品、別の末尾型番、非表示の仮データ、材料在庫、包装の入数を混ぜない。
3. Jevへ、在庫状態・在庫数量・配送表示それぞれを支える根拠IDを選ばせる。「該当なし」も用意する。暫定のルール判定やテストの正解ラベルはモデルへ渡さず、原文と構造の情報を渡す。
4. ページに存在する根拠IDであること、ルールが読んだ数量と整合することを検査する。存在しないID、不正な確率分布、低い一致度、モデルとの不一致は保留する。異なる数量や在庫状態の矛盾は、Jevの高い値でも上書きしない。
5. 取得した結果を掲載上の観測として管理メモに保存する。仕入れ可能数量・配送営業日数・担当者承認へは自動転記しない。

Jevの選択肢はTypeSafeのChoiceを使用する。[公式API仕様](https://docs.typesafe.ai/api)に合わせ、選択したIDと全選択肢の分布を検査する。採用には先頭の値0.8以上、次点との差0.2以上を要求している。これは暫定の保留基準であり、実在庫が正しい確率や確約率ではない。APIが利用できない場合は、根拠付きのルール抽出として明示する。

商品同一性の判定と同じJevリクエストに質問を含め、通常チャットでのAPI往復を追加しない。お客様向けの返答は引き続き必要数量の在庫・発送日が未確定であることを示す。

## 精度を自分たちで測るための評価

開発で正解を付けた架空32例を用意した。通常例17件・追加の難例15件。入数と在庫、別商品の表、末尾型番違い、関連商品、材料在庫、過去の数量、非表示要素、矛盾、構造化データ、6000文字より後ろの表示などを含む。これらは会社による回答でも実際の在庫でもない。

ルールを作りながら確認した回帰評価用の例であり、独立した未見データのテストではない。正解ラベルをモデルへ送ることはせず、実APIの出力を保存して比較した。

最終の実API試験（`v3/live-results.json`）では、在庫状態・数量・配送区分の3項目すべてが正解に一致したのが31/32例。掲載数量を採用した9例はすべて正しい数値だった。数量を取得できる正解例10件のうち1件は、モデルの一致度が基準を下回り保留した。

| 数量の確認 | 前回方式を再現した診断 | 今回の方式 |
| --- | --- | --- |
| 採用可能な数量表示を拾えた例 | 8例 | 9例 |
| 今回の用途で採用すべきでない表示を陽性とした例 | 4例 | 0例 |
| 取りこぼし・保留 | 2例 | 1例 |

前回方式は、構造を消した本文の先頭6000文字に「特定商品の完成品在庫数量の明記」を質問する診断。今回方式は型番の指定、構造化データ、表の対応、数値の抽出、矛盾の保留も含むため、**モデル単体の精度比較ではない**。前回診断の4例は、矛盾する数量・別末尾型番・関連商品・別商品セクション。数量の文字自体が存在しても、希望商品の数量として採用するのは不適切だった。

残った保留例は「1箱1000個入り。在庫：2個」。モデルは正しい根拠を最上位に選んだが、在庫状態・数量の判定値が採用基準に届かなかった。基準を下げて採用させず、原文と保留理由を担当者へ残す。

この標本で数量の誤採用がなかったことは、実サイト全体の誤判定率ゼロを意味しない。今後、実ページを人が確認して正解を付けた例を増やす。誤採用・取りこぼし・保留を別々に数え、失敗例を固定したテストへ追加し、修正後に再評価する。モデル自身の一致度をそのまま精度の点数にしない。

## 実HPの保存済みHTMLでも確認

前回取得したアジア技研（M3-5-SAO）、並田機工（YM4）、イーデンキ（BG-32YE）、タキゲン（A-452）の4標本を、新しいルールで再解析した。これらは実APIの架空32例とは別の確認。

- アジア技研の小箱入数を、在庫数として採用しない。
- 並田機工の材料在庫を、完成品在庫数として採用しない。型番の数字や「超短納期」という説明だけから具体的な出荷時期を採用しないことも回帰テストに追加した。
- イーデンキの一般出荷案内を、指定商品の出荷予定へ転用しない。
- タキゲンの静的HTMLで値が得られない場合は未確認を維持する。

この4標本から商品の引当・当社発送日を確認したという意味ではない。JavaScript表示、会員向け在庫照会、契約APIなどの取得範囲拡張は引き続き別の作業。

## 再実行・失敗例の追加

正解例：`tests/fixtures/availability-cases.ts`。実際に確認した誤判定を、原文・型番・期待する状態／数量／配送区分と一緒に新しい例として追加する。モデルの出力に合わせて正解を書き換えない。

```bash
# APIを使わずに抽出ルールを評価
npx tsx scripts/evaluate-page-availability.ts .data/verification/availability-classification-2026-10-16/rules

# 実Jev APIで照合。比較用の旧診断は独立したリクエストで実行
node --env-file=.env.local --import tsx scripts/evaluate-page-availability.ts --live .data/verification/availability-classification-2026-10-16/retest

# 回帰テスト
npx vitest run tests/page-availability.test.ts tests/sourcing.test.ts
```

結果は `live-results.json`／`rule-results.json`。期待値・出力・保留理由・根拠・数量の採用数と正解数を保存する。実API試験の `batch-*.json` は認証情報を含めず、新しい質問・原文・回答の確認に使える。初回の比較は新旧を同じ状態へ載せていたため参考扱いとし、`v2`・`v3` は状態を分離した。

## 検証と運用上の範囲

全体の単体テスト16ファイル258件が成功。その後、実HP再解析で見つけた定性的な短納期表現と、在庫状態／数量の矛盾の3例を追加し、最終の関連テスト56件も成功した。型チェック・本番ビルド成功。管理画面のPC／スマートフォンE2Eは2件とも成功し、根拠の展開、掲載数量から確認済み数量へ自動転記しないこと、確認後の概算と見積フォームへの引継ぎ、掲載先情報の非公開を確認した。集計は `.data/verification/availability-classification-2026-10-16/validation.json` に保存した。

仕分けの改善は、確認作業に使える情報を増やすためのもの。HPにない当社向け引当や当社からの発送期限を生成する処理は追加していない。必要数量の確保、経由輸送、検品、当社発送の確認と会社承認は、前回のQ006・Q007・Q009に集約した運用確認を継続する。

通常DB・過去の相談記録は変更していない。販売条件の設定・アプリの本番デプロイ・実注文は行っていない。
