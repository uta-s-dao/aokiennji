# 調達結果の記憶

管理画面の会話詳細 → AI調査メモ → 各調達先の「発注・入荷の実績を記録／確認」で使用する。

- 調達条件を確認済みで保存すると、確認条件とページ判定の根拠を自動保存する。条件確認だけでは購入成功に数えない。
- 外部で発注した場合は「外で発注済みを記録」を押す。型番・参照URL・当時の判定と条件を自動保存し、必要数量は同じ商品の会話から初期入力する。掲載在庫数や小箱入数を発注数に使わない。異なる数量で発注した場合は修正する。
- 実際に届いたら「全数入荷を記録」。分納は累計入荷数を入力し、発注数まで揃ってから全数入荷とする。調達不可・遅延・発注取消・返品・誤記録取消も残せる。
- アプリの既存の注文送信処理が送信済みになった場合は、型番と仕入先を識別できる明細ごとに発注履歴を自動保存する。入荷は注文管理画面で記録する。受注APIの受付番号は在庫・引当・入荷の証拠ではない。送信結果不明は発注済みの実績へ繰り上げない。
- 同じ型番・調達先について、実運用の全数入荷・調達不可・遅延を発注単位で集計する。返品・誤記録取消を購入成功から外し、デモを実運用から除外する。元の履歴は保持する。
- 次の新しい調査では、同じ完全型番で全数入荷した参照URLを最大2件優先候補として再取得する。現在の価格・在庫・型番一致を改めて検証し、過去の承認・在庫数量・納期をコピーしない。検索障害時も実績URLの再確認を試みる。通常の15分の会話内キャッシュ／明示的な条件確認の期限は従来どおり適用される。

記憶はSQLiteの`procurement_cases`（発注ごとの状態と当時の証拠）と`procurement_events`（追記型の操作履歴）に保存する。結果の更新と履歴はトランザクションで保存し、同一の操作IDの再送を二重計上しない。APIは管理者認証と同一オリジン確認が必要。顧客向けチャットへ仕入先・仕入価格・内部履歴を渡さない。

表示日時は記録日時であり、実際の発注日・入荷日や営業日ベースのリードタイムを推定する機能ではない。過去の成功を今回の在庫、10個全数の引当、当社からの発送期限の確約には用いない。AI自身の判定を正解ラベルとして学習し直す仕組みでもない。

外部のメール・購入サイト・受発注システムを監視する接続は未実装。完全自動化には注文番号・型番・数量を対応付けられる既存記録が必要なため、会社への確認事項Q012へまとめている。現状は判定・条件確認・アプリ内送信を自動保存し、外部での結果は最小限のボタン入力で蓄積する。自動発注を新たに有効化する変更は含まない。
